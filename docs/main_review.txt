Analysis of the Three Versions
1. 
main_pre_nemo.py
This is the most detailed and complete version, closely aligned with the latest ADRs and the project's documented state.

Strengths:

Full ADR Compliance: Explicitly implements ADR-018 (Service-Oriented Orchestration), ADR-019 (Master Shell Pattern concept via internal orchestration), ADR-020 (Config-Driven ETL), and ADR-021 (Decoupling BATCH_ID from PL/SQL).
Robust Audit Trail: Properly implements the SYS_BATCH_LOG pattern with 
create_batch_record
 and 
update_batch_status
, using task_name as source_system (which encodes session type per ADR-010 consolidation).
Clear Separation of Concerns: Uses singleton services (alert_manager, db_transformer) correctly instantiated at module level.
Graceful Error Handling:
Tier 1 alerts for local/cloud mismatches (logged, backup retained).
Tier 2 alerts for systemic failures (Pushover).
Cloud sync failures are non-fatal (logged as warning, pipeline continues).
Health check failures trigger Tier 2 alerts and halt execution.
Config-Driven:
Uses config.get() for YAML access.
Reads log_level, backup_dir from config.
OCI PAR URL resolution checks both YAML and .env (via config.env.oci.config_path).
CLI Structure:
Three sub-commands: scrape, transform, 
maintain
.
scrape uses --task (which includes session type, e.g., price_ohlcv_pre), eliminating the need for --session-type (consistent with ADR-010).
Global --skip-health-check flag.
Initialization Order:
Health check → Scraper execution → Cloud sync → Post-action ETL → Audit update.
Matches the documented flow in 
temp_note.md
 and ADR-019.
Logging: Uses standard library logging with configurable level and optional file output.
Weaknesses:

Slightly more verbose, but this is justified by the need for robustness in a 1GB RAM environment.
The finally block for driver cleanup is correctly placed in 
BaseScraper.run()
 (per ADR-018.5 and ADR-003), so no duplication is needed here.
Verdict: This version is production-ready and reflects the "Current Focus" state described in 
ACTION_LOG.md
 (Orchestration Layer In Progress, moving toward Shell-wrapped pipeline). It integrates all certified components and adheres strictly to the approved ADRs.

2. 
main_pre_gemma.py
A simplified version that reduces abstraction but loses some critical enterprise features.

Strengths:

Simpler to read and understand.
Correctly uses 
get_scraper
 from 
factory.py
.
Implements basic audit trail (
create_batch_record
, 
update_batch_status
).
Attempts to trigger post-scrape ETL via post_{task_name} group.
Weaknesses:

Missing Health Check Integration: Does not call 
StartupHealthChecker.run()
 unless --skip-health-check is not used — but the health check logic is not actually invoked in the main flow. The 
run_health_check()
 function is defined but only called conditionally, and even then, it lacks the Pushover alert on failure (a key part of ADR-018.2).
Incomplete Cloud Sync Logic:
Attempts to read OCI PAR URL from config.env.oci.bucket_name (incorrect — this should be the bucket name, not a PAR URL).
Falls back to config.get("system", {}).get("oci_par_url") — this part is correct, but the primary source is wrong.
No warning log if cloud sync is skipped due to missing config (unlike 
main_pre_nemo.py
).
No AlertManager Integration:
Uses alert_manager.send_tier2_alert on failure, but the alert_manager singleton is imported and instantiated — however, there is no Tier 1 warning logic for mismatches.
No integration with 
BackupManager
 for local persistence verification (though this may be handled in 
BaseScraper
).
ETL Triggering:
Calls db_transformer.trigger_group(post_group) but does not handle exceptions in a way that halts the pipeline and triggers Tier 2 alerts (it does sys.exit(1), but without logging the full traceback or ensuring audit status is updated before exit).
Logging: Uses basic config but does not allow file logging via config (unlike 
main_pre_nemo.py
).
Verdict: This version is incomplete and risky for production. It omits critical safety layers (health check alerting, proper config resolution, Tier 1/2 alerting distinction) and does not fully implement the orchestration patterns defined in ADR-018 through ADR-021.

main_pre_gemini.py
A middle ground — cleaner than 
main_pre_nemo.py
 but more complete than 
main_pre_gemma.py

Strengths:

Clean, readable structure.

Implements the three sub-commands (scrape, transform,

Correctly uses task_name (which includes session type) for audit context.

Post-action ETL triggering via post_{task_name} group is present and conditional.
Weaknesses:

Incorrect OCI PAR URL Source:
Uses config.get("oci", {}).get("par_url") — but in the provided

The correct path (as seen in

Health Check Alerting:

Missing Audit Initialization for Transform/Maintain:

This violates the BRD's "High-Tolerance Anti-False-Alarm" strategy and the documented consistency verification layer.
Logging:
Uses basic config but does not support file logging via config.get("system", {}).get("log_file").
Verdict: This version is better than 
main_pre_gemma.py
 but still incomplete for production use. It fails to correctly resolve the OCI PAR URL (a critical path for cloud backup), omits audit logging for transform/maintain operations, and lacks the Tier 1/2 alerting distinction for data consistency.

二、 为什么选择 
main_pre_nemo.py
？
符合 Master Shell (ADR-019) 契约： 在 1GB RAM VM 环境下，外部是通过 
run_task.sh
 调度（执行 cleanup -> main.py -> cleanup）。nemo 版在 
main()
 统一聚合 exit_code，捕获异常后触发 Tier 2 Pushover 报警并返回退出码 1，让外层 Shell 能够精确感知成败并触发后置清理或 Supabase Heartbeat。
Post-Action ETL 强一致性： nemo 将 
_trigger_etl_group(post_group)
 放在标记 SUCCESS 之前，一旦 PL/SQL 过程报错，整个批次置为 FAILED 并触发 Pushover，保证了 ODS 落地与 BDI 转换在审计上的完整闭环。
架构解耦度高： 显式注入 scraper = scraper_cls(db_op=db_operator)，与工厂模式和底层依赖完美贴合。
三、 对 
main_pre_nemo.py
 的微调建议（落地前的最后优化）
main_pre_nemo.py
 已经具备 95% 以上的生产完成度，建议在最终采纳为 src/main.py 时加入以下两点微调：

OCI PAR URL 字段对齐： 检查 
config.py
 中的 
OCIConfig
，目前类定义中包含 config_path、bucket_namespace、bucket_name。如果在 .env 里存的是 PAR 完整 URL，请确保统一从 config.env.oci.config_path 或 config.get("system", {}).get("oci_par_url") 读取，保持两处命名完全一致。
显式关闭 DB 连接池： 在 
main()
 的最外层或 sys.exit 前，增加一个轻量级的连接池释放防护（如 db_operator.close()），防止进程退出时连接悬挂。
