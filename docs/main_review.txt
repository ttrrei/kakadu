P0：并发 worker 正在同时写同一个 JSONL 文件和同一个 RunReport
当前非 Selenium 的 iterative 路径会把同一个 batch_bak 和同一个 report 对象传进多个 future。 

而 worker 内部会同时：

调用 batch_bak.append_records(records) 写同一个 records.jsonl；

修改 report.extracted_records_count；

修改 report.success_symbols；

修改 report.backed_up_count。 

BatchBackupContext.append_records() 本身没有 mutex / lock，却会多次执行写文件、flush、fsync 和 record_count += written。 

这会导致：

JSONL 行可能交错或损坏；

record_count 可能发生竞争丢失；

RunReport 的计数可能不准确；

manifest 中的 record_count 与实际文件行数不一致；

随后 Tier 1 / Tier 2 判断建立在不可靠的数据上。

正确修复方式
不要给当前 worker 共享对象简单加锁作为首选方案。
更符合 Thin-Edge、也更容易测试的实现是：

worker 只负责抓取，返回：

symbol, records
主线程在 future.result() 后，串行地：

累加 extracted count；

写 JSONL；

累加 backup count；

将记录放�� DB buffer；

达到 batch size 后调用 insert_batch()；

合并 InsertResult。

worker 线程不接触 BatchBackupContext、RunReport 和 DbOperator。

这样可以保留 bounded in-flight 的内存优势，同时保证备份、审计和 DB 写入统计都是单线程、可重现的。

P0：UploadManager 仍在调用已删除的旧 BackupManager API
新的 BackupManager 已改成 batch 级方法：

get_batch_dir(...)；

start_batch(...)；

clear_batch_dir(...)。 

但 UploadManager 仍调用旧 API：

get_task_dir(...)；

clear_task_dir(...)。 

这两个方法当前已不存在。只要未来完整 main.py 调用了 cloud sync，上传会抛出 AttributeError。如果主调度器遵循你之前设定的 Tier 1 云同步降级策略，该错误甚至可能只被记录为 warning，造成“云同步已配置但从未成功”的假象。

正确修复方式
将上传接口改为 batch 级别，例如：

sync_to_cloud(
    table_name=report.target_table,
    batch_id=report.batch_id,
    backup_path=report.backup_path,
    manifest=manifest,
)
上传对象路径建议：

<ODS_TABLE>/<YYYY-MM-DD>/<BATCH_ID>/records.jsonl
<ODS_TABLE>/<YYYY-MM-DD>/<BATCH_ID>/manifest.json
清理的前提应当是：

records 文件上传成功；

manifest 上传成功；

远端 checksum / content-length 校验通过；

本地 backed_up_count == inserted_db_count；

仅删除该 batch 的目录。

当前 UploadManager 只要 PUT 返回成功就清理数据，这仍未达到“验证后清理”的目标。
