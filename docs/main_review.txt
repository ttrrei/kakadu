审计失败被吞掉，可能产生“业务成功但没有审计记录”的静默失败

Nemo 对 create_batch_record() 的异常只记日志并继续抓取。

更严重的是，底层 DbOperator.create_batch_record() 在 Oracle 错误时 rollback 并记录日志，但不重新抛出异常，也不返回失败标志。update_batch_status() 也是同样的行为。

这会造成：

RUNNING 插入失败；

Nemo 继续执行 scraper、上传和 ETL；

SUCCESS 更新也可能失败但被吞掉；

主程序仍返回 0。

这直接违背了你文档中的“零静默失败”和严格批次生命周期要求。

建议：

将 create_batch_record() 与 update_batch_status() 改成：成功返回 None/True，数据库异常必须向上抛出。

create_batch_record() 失败应立即终止任务并触发 Tier 2；否则没有可靠的批次血缘。

FAILED 状态写入失败时，应记录 CRITICAL，并让外部 Shell / heartbeat 能观察到非零退出码。

可考虑给 SYS_BATCH_LOG.BATCH_ID 加唯一约束，避免重复 batch id 导致更新多行或审计歧义。

# src/db_operator.py 改造后

    def create_batch_record(self, batch_id: str, task_name: str, source_system: str = "INTERNAL") -> None:
        """Insert an initial 'RUNNING' record into SYS_BATCH_LOG.
        Raises oracledb.Error / Exception on failure (Fail Fast).
        """
        sql = """
            INSERT INTO EQUITY.SYS_BATCH_LOG 
            (BATCH_ID, LAYER, PIPELINE_NAME, STATUS, SOURCE_SYSTEM) 
            VALUES (:batch_id, 'ODS', :pipeline, 'RUNNING', :source)
        """
        conn = self.get_connection()
        cursor = conn.cursor()
        try:
            cursor.execute(sql, batch_id=batch_id, pipeline=task_name, source=source_system)
            conn.commit()
            logger.info(f"Batch record created: {batch_id} for task {task_name}")
        except Exception as exc:
            conn.rollback()
            logger.error(f"Failed to create batch record in SYS_BATCH_LOG: {exc}")
            raise  # <--- 必须向上抛出！让调度层感知
        finally:
            cursor.close()
            self._pool.release(conn)

    def update_batch_status(self, batch_id: str, status: str, error_message: str = None) -> None:
        """Update the status of a batch in SYS_BATCH_LOG.
        Raises oracledb.Error / Exception on failure.
        """
        sql = """
            UPDATE EQUITY.SYS_BATCH_LOG 
            SET STATUS = :p_status, 
                END_TIME = SYSTIMESTAMP, 
                ERROR_MESSAGE = :p_err 
            WHERE BATCH_ID = :p_bid
        """
        conn = self.get_connection()
        cursor = conn.cursor()
        try:
            cursor.execute(sql, p_status=status, p_err=error_message, p_bid=batch_id)
            conn.commit()
            logger.info(f"Batch record updated: {batch_id} -> {status}")
        except Exception as exc:
            conn.rollback()
            logger.error(f"Failed to update batch status in SYS_BATCH_LOG: {exc}")
            raise  # <--- 必须向上抛出！
        finally:
            cursor.close()
            self._pool.release(conn)

def handle_scrape(task_name: str) -> int:
    batch_id = uuid.uuid4().hex
    logger.info(f"=== SCRAPE START | Task: {task_name} | Batch: {batch_id} ===")

    try:
        # 1. Audit Entry (RUNNING) - 必须在主 try 块内！失败直接 Fail Fast
        db_operator.create_batch_record(
            batch_id=batch_id, 
            task_name=task_name, 
            source_system=task_name
        )

        # 2. Factory & Execution
        scraper_cls = ScraperFactory.get_scraper(task_name)
        scraper = scraper_cls(db_op=db_operator)
        target_table = scraper.target_table

        if not target_table:
            raise KeyError(f"Scraper '{task_name}' missing 'target_table' in config.yaml")

        logger.info(f"Executing Scraper: {scraper_cls.__name__} -> Target Table: {target_table}")
        scraper.run(job_name=task_name, batch_id=batch_id)

        # 3. Cloud Sync (Post-Ingestion, 保持 Tier-1 容错，不阻断主流程)
        _sync_cloud_backup(target_table)

        # 4. Post-Action ETL
        post_group = f"post_{task_name}"
        etl_groups = config.get("etl_groups", {})
        if post_group in etl_groups:
            _trigger_etl_group(post_group)
        else:
            logger.info(f"No post-action ETL group defined for '{post_group}'. Skipping.")

        # 5. Audit Success (包含此步！如果 update 失败，冒泡到 except 记录 FAILED 并报警)
        db_operator.update_batch_status(batch_id=batch_id, status="SUCCESS")

        return 0

    except Exception as e:
        err_msg = str(e)
        logger.error(f"=== SCRAPE FAILED | Task: {task_name} | Batch: {batch_id} | Error: {err_msg} ===")
        
        # 尽最大努力更新为 FAILED，如果此时 DB 彻底挂了，记录 CRITICAL

            db_operator.update_batch_status(batch_id=batch_id, status="FAILED", error_message=err_msg)

        # 触发 Tier 2 Pushover 警报 (系统致命故障)
        alert_manager.send_tier2_alert(
            f"Kakadu Scrape Failure\nTask: {task_name}\nBatch: {batch_id}\nError: {err_msg}"

但 BaseScraper._run_iterative() 会遍历完整 symbols_gen，为每个 symbol 一次性创建 future，并将所有 future 放进 future_to_symbol 字典。符号数达到两千时，任务队列、future 和引用都留在内存中，这不是 O(1)。

同时，配置中给 price_ohlcv_pre 设置了 max_workers: 20，且 AFR、分析师任务也设置了 10 个 worker。 数据库连接池又允许最大 40 个连接。

在 1GB VM 上，这组参数风险很高，即使每个单独组件看起来都“轻量”。

建议：

用有界 in-flight 队列，不要一次性提交所有 symbol。

max_workers 应控制在 1–4，并按 scraper 类型分别设置。

DbOperator 连接池建议是 min=1, max=2~4，而非 40。

若 scraper 使用单一 Selenium driver，禁止多线程共享 driver；Selenium 任务应始终 max_workers=1。

必须加 RSS/峰值内存监控和全市场压测，达标后再上 crontab。

1. 修复 
BaseScraper
 中的任务提交：采用“有界并发流（Bounded In-Flight Stream）”
不需要引入第三方库，用 Python 标准库的标准生成器推导即可将并发窗口限制在 max_workers * 2，实现真正的 $O(\text{workers})$ 内存占用：


Apply
# src/base_scraper.py 改造：
def _run_iterative(self, job_name: str, batch_id: str | None = None):
    logger.info(f"Executing in ITERATIVE mode with {self.max_workers} threads...")
    
    success_count = 0
    fail_count = 0
    driver = self.get_driver()
    symbols_gen = self._get_symbol_generator()
    buffer = []
    
    # 限制同时在内存中飞行的任务数为 workers * 2
    max_in_flight = max(self.max_workers * 2, 4)

    with ThreadPoolExecutor(max_workers=self.max_workers) as executor:
        future_to_symbol = {}
        
        # 1. 预填满有界窗口
        for symbol in symbols_gen:
            future = executor.submit(self._process_single_symbol, driver, symbol)
            future_to_symbol[future] = symbol
            if len(future_to_symbol) >= max_in_flight:
                break

        # 2. 消费一个，补充一个，内存始终维持在 O(workers) 级别
        while future_to_symbol:
            # 等待最早完成的一个
            for future in as_completed(future_to_symbol):
                symbol = future_to_symbol.pop(future)
                try:
                    result = future.result()
                    if result:
                        records = result if isinstance(result, list) else [result]
                        buffer.extend(records)
                        success_count += 1
                        
                        if len(buffer) >= self.batch_size:
                            self.db.insert_batch(self.target_table, buffer, batch_id=batch_id or job_name)
                            buffer = []
                except Exception as e:
                    logger.error(f"Failed to process symbol {symbol}: {e}")
                    fail_count += 1

                # 补充新任务到线程池
                try:
                    next_symbol = next(symbols_gen)
                    new_future = executor.submit(self._process_single_symbol, driver, next_symbol)
                    future_to_symbol[new_future] = next_symbol
                except StopIteration:
                    pass
                
                # 重新计算 as_completed（保持动态循环）
                break

三、 区分：什么是必须做的修改？什么是过度工程？
评审人指出了真问题，但给出的建议里有轻重之分：

❌ 评审建议中的“过度工程部分”：
