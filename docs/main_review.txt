P0-1：数据库事务 rollback 后，InsertResult.inserted_count 会虚报成功写入数
insert_batch() 在每个 chunk 返回成功时立即增加 inserted_count，但它只在所有 chunk 都处理完成后才调用 conn.commit()。 

如果发生下面的情况：

前几个 chunk 的 executemany() 成功；

后面的 chunk 发生非 oracledb.Error 的异常；

外层进入 except 并执行 conn.rollback()；

前面所有尚未提交的记录都会回滚；

但 inserted_count 没有重置为 0。 

此时 RunReport 会把已经回滚、数据库中实际不存在的记录报告为“已入库”。而后续 Tier 1 对账和成功审计都会使用这个虚假的计数。 

必须修改
推荐按你 BRD 的“小批量提交”原则，在每个 chunk 成功完成后立即 commit：

for start in range(0, attempted_count, batch_size):
    chunk = prepared_records[start:start + batch_size]
    chunk_inserted, chunk_dropped = self._execute_chunk(cursor, conn, sql, chunk)
    conn.commit()
    inserted_count += chunk_inserted
    dropped_count += chunk_dropped
如果坚持把所有 chunk 放进同一事务，那么 outer rollback 时必须：

inserted_count = 0
dropped_count = attempted_count
我建议每个 5–10 条 chunk commit，因为这与项目对小批次 PURE-INSERT 的设计一致。 

P0-2：出现 Tier 1 数据不一致时，主流程仍会上传并删除本地备份
目前的 BaseScraper.run() 会在：

report.backed_up_count != report.inserted_db_count
时调用 check_tier1_mismatch()，但只记录 warning，随后仍返回 RunReport。 

handle_scrape() 收到 report 后，无条件调用 _sync_cloud_backup()。 

而 UploadManager.sync_to_cloud() 在 HTTP PUT 成功后，立刻执行：

self.backup_manager.clear_batch_dir(table_name, batch_id, date_str)
删除本地 batch 目录。 

这违反了你定义的 Tier 1 行为：**本地备份与 DB 入库数不一致时，必须保留备份。**规范明确规定 cloud sync 失败和数据不一致都不能让本地证据被清理。 

必须修改
在 RunReport 中增加一个明确字段，例如：

has_tier1_mismatch: bool = False
发生 mismatch 时设为 True。随后传 report 或 policy 给同步函数：

_sync_cloud_backup(
    target_table=report.target_table,
    batch_id=report.batch_id,
    allow_local_purge=not report.has_tier1_mismatch,
)
在 UploadManager.sync_to_cloud() 中：

可以选择仍上传 ZIP，保留远端取证；

但 allow_local_purge=False 时绝不能调用 clear_batch_dir()；

记录包含 batch id、backup count、inserted count 的 Tier 1 日志。

P0-3：所谓“验证后清理”目前只是验证 HTTP 2xx，并未验证上传内容
UploadManager 的参数包含 manifest，但当前实现没有使用它。 

现有逻辑只是：

创建 ZIP；

PUT 到 OCI；

response.raise_for_status()；

删除本地 batch。 

这只能证明服务器返回 2xx，不能证明：

远端对象确实可以读取；

上传对象字节数正确；

ZIP 内容完整；

records.jsonl 与 manifest.json 都被包括；

checksum 匹配；

本地数据可以安全清理。

必须修改
建议最少完成以下闭环：

创建 ZIP 后计算：

zip_size_bytes

zip_sha256

PUT 时带 Content-Length，当前已做到。 

PUT 后执行一个可行的远端校验：

若 PAR 允许 HEAD：用 HEAD 确认对象存在、Content-Length 匹配；

若 PAR 不支持 HEAD：使用 OCI SDK / 专门的 read PAR 下载或读取 object metadata；

若完全无法读取远端：至少把本地 ZIP 的 checksum、size 和 manifest 一并作为对象 metadata 或单独上传 manifest。

确认远端对象校验通过后，才允许清理 batch 目录。

如果校验失败，抛异常；主流程只记录 Tier 1、保留本地 batch。

你的 batch backup 已经生成了 JSONL checksum、record count 和 manifest，这是非常好的基础。 现在只需把它真正纳入 upload verification。
