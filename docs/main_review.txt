P0：数据库写入失败仍可能被标记为 SUCCESS
虽然审计写入失败已经会抛异常，但数据插入方法 insert_batch() 仍会吞掉整体插入错误：

except Exception as exc:
    conn.rollback()
    logger.error(...)
然后仍返回 effective_batch_id。 

单条 fallback 插入失败时也只是记录“Dropped record”，没有返回实际成功数或失败数。 

而 BaseScraper 的 success_count 统计的是“scrape_one() 返回了数据”，不是“数据实际成功写入 Oracle”的条数。 

这可能造成以下情况：

API 成功抓到 100 条记录；

本地备份也写成功；

Oracle 因字段、连接或 SQL 错误而一条未写入；

insert_batch() 吞掉错误；

success_count > 0；

main_v3_gemini.py 最终写 SUCCESS。

这意味着此前的“本地备份 vs DB 写入计数”的 P0 问题尚未真正修复。

推荐修复方式
不要让 insert_batch() 仅返回 batch_id；应返回显式结果，例如：

@dataclass(frozen=True)
class InsertResult:
    attempted_count: int
    inserted_count: int
    dropped_count: int
然后 BaseScraper.run() 汇总并返回：

@dataclass(frozen=True)
class RunReport:
    target_table: str
    extracted_count: int
    backed_up_count: int
    insert_result: InsertResult
    failed_symbol_count: int
    backup_path: str
最后在 main 中：

inserted_count == 0 且 extracted_count > 0：Tier 2 + FAILED；

inserted_count != backed_up_count：调用 check_tier1_mismatch()；

只有关键条件满足时才进入 Post-ETL 和 SUCCESS。

目前 AlertManager 已经具备 Tier 1 mismatch 函数，但 Gemini/Nemo 都未调用它。 

P1：云同步配置语义仍不一致
当前 config 使用：

oci:
  enabled: true

但 Gemini/Nemo 不读取该字段；它们只读取：

system.oci_par_url

config.env.oci.config_path

找不到 URL 时仅记录 INFO 并返回成功。 

这将导致“配置显示已启用、实际没有上传”的危险假象。

推荐修复方式
配置和代码统一成一种明确模型：

oci:
  enabled: true
环境变量：

OCI_PAR_URL=https://objectstorage...
配置对象：

@dataclass
class OCIConfig:
    enabled: bool = False
    par_url: str = ""
调度逻辑：

oci.enabled	OCI_PAR_URL	行为
false	任意	INFO：主动不启用同步。
true	有效 URL	执行同步。
true	缺失/非法	Tier 1 Warning；生产环境可选择拒绝启动。
另外，建议废弃把 PAR URL 存入 OCI_CONFIG_PATH 的做法；该名字容易被理解为 OCI SDK 的 config 文件路径，而不是预认证上传 URL。

P1：上传后仍然是“成功 PUT 即清理”，没有验证后清理
当前 UploadManager 的流程是：

压缩；

PUT；

raise_for_status() 成功；

立即 clear_task_dir()。 

但设计要求是：上传和验证后，才清理本地文件。 

推荐修复方式
建议采用 batch 级别的备份对象，而不是“table + day”级别：

/home/ubuntu/backup/
  ODS_PRICE_TICK/
    2026-09-24/
      <batch_id>/
        records.jsonl
        manifest.json
manifest.json 至少记录：

batch_id

table_name

record_count

SHA-256

文件大小

创建时间

上传对象路径也按 batch 分隔：

ODS_PRICE_TICK/2026-09-24/<batch_id>/records.jsonl
ODS_PRICE_TICK/2026-09-24/<batch_id>/manifest.json
然后：

上传数据和 manifest；

验证 HTTP 成功；

验证远端对象或至少验证 checksum / content length；

完成 DB count 对账；

仅当上述步骤全部成功时清理此 batch 的本地目录；

mismatch 或上传失败时必须保留本地文件。

P1：内存问题已大幅改善，但并未完全收敛到 1GB 安全值
bounded in-flight 已经解决了全量 future 堆积问题。 

不过当前配置仍允许：

price_ohlcv_pre.max_workers: 20；

多个任务为 10 worker。 

即使 Oracle pool 降为 5，20 个 HTTP worker、响应对象、JSON 解析和 backup 写入仍可能不适合 1GB VM。

推荐值
HTTP/API iterative scraper：max_workers: 2~4

Selenium scraper：固定 max_workers: 1

Oracle pool：当前 max=5 已显著改善；若真实负载不高，可以进一步评估 max=2~3

max_in_flight：保持在 max_workers * 2 是合理的，但应加入配置上限，例如 max_in_flight <= 8

建议的下一步:

修改 DbOperator.insert_batch()，返回实际 attempted / inserted / dropped 计数。

修改 BaseScraper，返回 RunReport。

修改 BackupManager，用 batch 级 JSONL 文件替代按 symbol 覆盖式 .json 文件。

在 main.py 调用 AlertManager.check_tier1_mismatch()。

当写入为 0、失败比例超阈值、或数据缺失严重时，抛出异常、写 FAILED、发 Tier 2。

将云端清理逻辑改为“上传 + 校验 + DB 对账成功后”执行。

新增明确的 OCI_PAR_URL 环境变量；

新增 oci.enabled 的代码读取；

给“主动禁用”和“错误缺失配置”不同日志等级；

写对应单元测试。
